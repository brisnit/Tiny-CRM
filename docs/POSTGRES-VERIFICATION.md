# PostgreSQL verification

The previous hardening report graded portability YELLOW with the note that it was
"argued, not proven" — the schema was written to be provider-agnostic, but the
application had never been executed against PostgreSQL.

It has now.

---

## What was executed, and where

**Engine:** PostgreSQL 17.10 (`x86_64-apple-darwin24.6.0`), a real `postgres`
process, not a mock or an emulation.

This machine has no Docker, no Homebrew and no system PostgreSQL. Rather than
report the same gap twice, `scripts/pg.mjs` starts a cluster from the binaries in
`@embedded-postgres/darwin-arm64` — the upstream Zonky builds, the same ones the

## Findings

Five differences mattered. Four were fixed; one is documented as a permanent,
engine-specific behaviour.

### F-1 — Prisma's migration history is provider-locked *(fixed)*

**Severity: high.** The previous report described switching engines as "a
one-word change in `schema.prisma`". It is not.

`prisma migrate deploy` refused outright:

```
Error: P3019
The datasource provider `postgresql` specified in your schema does not match
the one specified in the migration_lock.toml, `sqlite`.
```

`migration_lock.toml` records the provider a history was authored against, and
the SQL inside is written in that engine's dialect — SQLite's `DATETIME` and
inline `PRIMARY KEY` versus PostgreSQL's `TIMESTAMP(3)` and named constraints.
One history cannot serve both.

**Fix.** Two histories, both generated from the same provider-agnostic schema:

```
prisma/migrations/            SQLite      — development and the fast suite
prisma/migrations-postgres/   PostgreSQL  — every deployed environment
```

`prisma7.config.ts` selects the directory from `DATABASE_URL`. The PostgreSQL
history is a squashed `init` regenerated by
`scripts/sync-postgres-migration.mjs`, which refuses to squash once more than one
migration exists — after the first real deployment, incremental migrations are
added with `prisma migrate dev` instead.

### F-2 — `contains` is case-insensitive on SQLite and case-sensitive on PostgreSQL *(fixed in the previous pass, verified here)*

Prisma compiles `contains` to `LIKE`. SQLite's `LIKE` folds ASCII case;
PostgreSQL's does not. Search verified in development would have quietly started
missing results in production.

The `contains()` helper in `src/lib/db.ts` applies `mode: "insensitive"` on
PostgreSQL, which the SQLite connector rejects. The differences probe confirms
the underlying divergence and that the helper closes it:

```
LIKE   bare `contains` is case-INsensitive    SQLite: true    PostgreSQL: false
LIKE   app helper matches both cases          SQLite: true    PostgreSQL: true
```

### F-3 — `%` and `_` are unescaped wildcards on both engines *(fixed)*

Not a portability difference — a shared correctness and cost bug, found by the
same probe.

Prisma does not escape LIKE metacharacters. Searching `RFP_2026_014` also matched
`RFPX2026Y014`, and `?q=%` matched **every row in the workspace** — the cheapest
way for a signed-in user to force the most expensive query in the product.

**The two engines then diverge on the fix**, which is the portability half:

| | Escaped term `RFP\_2026` |
|---|---|
| PostgreSQL | matches 1 — backslash is the default LIKE escape character |
| SQLite | matches 0 — **no default escape character**; the backslash is literal |

So the term is escaped on PostgreSQL, where production runs, and left alone on
SQLite. On both engines a wildcard-only term is refused at the data layer
(`isSearchable`), which closes the cost half everywhere.

### F-4 — a circular foreign key makes a logical restore impossible *(fixed)*

**Severity: high.** Found by running `scripts/backup-test.mjs`, which failed at
the restore step:

```
insert or update on table "Company" violates foreign key constraint
"Company_primaryContactId_fkey"
```

`Company.primaryContactId → Contact.id` and `Contact.companyId → Company.id`
form a cycle. It is the correct data model — an account has a main person, a
person works at an account — and no table ordering can satisfy it. A team would
have discovered this during an incident, holding a backup they could not load.

**Fix.** `prisma/postgres/003_deferrable_constraints.sql` makes every foreign key
`DEFERRABLE INITIALLY IMMEDIATE`. Normal operation is unchanged: a dangling write
still fails on the statement that makes it. A restore can now
`SET CONSTRAINTS ALL DEFERRED` and have the whole graph verified once at COMMIT.
Deferring rather than disabling — the constraints are still enforced, just later.

### F-5 — a superuser bypasses row-level security *(documented; the app must not use one)*

`FORCE ROW LEVEL SECURITY` binds the table owner. It does **not** bind a
superuser. A verification run connected as the bootstrap superuser saw every row
with the policies fully applied:

```
SELECT count(*) FROM "Contact"   -- as tinycrm (superuser):  9
SELECT count(*) FROM "Contact"   -- as tinycrm_app:          0
```

This is PostgreSQL behaving as documented, and it is the single most likely way
for a deployment to believe it has a second isolation layer and not have one.

**Handling.** `rlsStatus()` in `src/lib/tenant-db.ts` asks the database which
role it is connected as, and `src/instrumentation.ts` logs at **error** level on
every boot when the connection is a superuser or the policies are absent. The
deployment checklist and `env.production.example` both say to point
`DATABASE_URL` at `tinycrm_app`. See `docs/RLS.md`.

## Differences checked and found equivalent

`scripts/db-differences.ts` runs the same 29 probes against either engine.
Everything below behaved identically on SQLite and PostgreSQL 17.

| Area | Observation |
|---|---|
| **Case sensitivity** | Equality is case-sensitive on both. `ORDER BY` produced the same sequence under `--locale=C`. |
| **Uniqueness** | Compound uniques reject duplicates and permit the same value in another workspace. Unique indexes treat case as distinct. Multiple NULLs are allowed in a UNIQUE column. |
| **Foreign keys** | A dangling reference is rejected on both. (SQLite enforces this only with `foreign_keys=ON`; the driver adapter sets it.) |
| **Cascade** | Deleting a company detaches its activity (`SetNull`); deleting a workspace cascades everything below it. |
| **Nullable relations** | A record with every optional FK null is valid. |
| **Dates** | Round-trip to the same instant with millisecond precision, read back as `Date`, range comparisons behave as instant comparisons. |
| **Transactions** | A thrown error rolls back every statement; a constraint violation aborts the whole transaction. |
| **Concurrent updates** | Exactly one of two racing version-guarded writes lands. 20–25 concurrent atomic increments all land, losing none. |
| **Aggregates** | `groupBy` returns a numeric count; `SUM` of an empty set is null on both. |
| **Search** | Application search is case-insensitive on both, and returns the same hit count. |

### Compound indexes

The one place the planners differ, and it is the planner being right rather than
a portability problem. On a six-row table PostgreSQL chose a sequential scan and
a sort where SQLite used the index — the correct choice at that size.

At scale the index is used, which is what the load test measures. On 100,000
contacts and 500,000 activities every screen query stayed well within budget,
and PostgreSQL was faster than SQLite on all twelve:

| Query | SQLite (XL) | PostgreSQL (XL) |
|---|---|---|
| Dashboard | 108 ms | **26 ms** |
| Contacts, page 1 | 113 ms | **44 ms** |
| Contacts, deep page | 121 ms | **48 ms** |
| Contacts search | 252 ms | **53 ms** |
| Analytics, 1 year | 254 ms | **81 ms** |
| Global search | 137 ms | **10 ms** |
| AI cleanup scan | 155 ms | **16 ms** |

The search figures are the trigram indexes from `001_search_indexes.sql` doing
their job; without them `ILIKE '%term%'` would be a sequential scan and slower
than SQLite, not faster.

## What this does *not* prove

- **`pg_dump` and provider point-in-time recovery.** The embedded package ships
  only `initdb`, `pg_ctl` and `postgres`. The restore drill uses `COPY`, which is
  the same mechanism `pg_dump` uses for table data, and restores the schema from
  the migration history. It proves the data round-trips and the relationships
  survive; it does not exercise pg_dump's own format. Verify that once against
  the real provider before launch — the deployment checklist says so.
- **A managed provider's behaviour.** Connection pooling (PgBouncer in
  transaction mode in particular), read replicas, failover and forced SSL are
  properties of the host, not of PostgreSQL. Notably, `SET LOCAL` — which the RLS
  tenant context depends on — is safe under transaction pooling, but session
  advisory locks would not be.
- **Sustained concurrent load.** The tests exercise correctness under
  concurrency (racing updates, 20-way increments, two workers claiming one job),
  not throughput under sustained multi-user traffic.
- **Extensions beyond `pg_trgm`.**

## Reproducing this

```bash
npm run pg -- start                      # PostgreSQL 17 on 127.0.0.1:55432
npm run test:pg                          # migrations, RLS, and every suite
npm run db:differences                   # the 29-probe engine comparison
npm run test:backup                      # back up, destroy, restore, verify
DATABASE_URL="$(npm run pg -- url --silent)" npm run test:perf -- --tier=xl
npm run pg -- destroy                    # remove the cluster
```

Against a PostgreSQL you already have, set `DATABASE_URL` and the same commands
use it instead. CI runs the equivalent against a `postgres:17` service container.

# POSTGRES VERIFIED: YES

The complete relevant suite — 318 automated tests across unit, security, tenant
isolation, AI boundary, lifecycle, portability and row-level security — executed
against a real PostgreSQL 17.10 server, along with both load-test tiers and a
backup/restore drill.

Two high-severity portability defects were found by executing rather than
reasoning, and both are fixed: the migration history could not be applied at all,
and the schema could not be restored from a logical backup.

The qualifications above are real and are listed rather than buried: `pg_dump`,
a managed provider's pooling and failover, and sustained load remain unverified.
